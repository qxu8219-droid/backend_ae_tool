# P0 严格同步实验记录

2026-10-23。要求是视频、28 关节、底盘、日志时间与进度游标对应同一份日志状态；允许共同延迟，不使用固定延迟补偿。

## 为什么不能直接给编码输出贴当前状态

SDK 的编码节点先取完成队列中的字节，再提交当前图像；公开接口没有返回这些字节对应的输入 ID。实际实验中图像标记经常比当前 Attribute 小一，但队列延迟不能假定恒为一。因此 `encoder_poll_capture_id` 仅表示调用时刻，不表示编码图像身份。

另一个独立问题来自渲染：6.2 实际启用 Real-Time Path Tracing 与 DLSS，启动参数 `anti_aliasing=0` 没有关闭这条路径的历史重建。动态标记出现混色。按[官方 SDG 工作流](https://docs.isaacsim.omniverse.nvidia.com/6.2.0/replicator_tutorials/tutorial_replicator_sdg_workflows.html)，每次更新姿态后、采集前设置 `/rtx-transient/post/dlss/forceParamReset=true`，源端连续 81 帧、后续 631 帧的原始像素验证全部通过。

## 目前的配对协议

1. 为每次采集分配递增的完整 uint32 ID，不在 seek 时重置，也不取模回绕。相机画面中实际渲染 64 个色块：32 位 ID 加上其大端四字节的 CRC32。
2. 关节与底盘直设后读回，冻结状态。绑定同一 writer payload 的 RGB 与 Attribute；只有原始 RGB 的 ID、CRC 和 Attribute 全部一致，快照才进入候选目录。
3. H.264 的 UUID SEI 携带 `p0.snapshot_catalog.v1`，最多包含 16 个不可变快照。它明确是候选集合，不宣称当前或上一快照就是该编码图像。
4. Chrome 在编码接收变换中解析 SEI，用独立递增 `packet_id` 将该 access unit 的目录和 WebCodecs 输出绑定。RTP/媒体时间戳只作诊断，不作业务身份。
5. 主线程从实际解码 VideoFrame 读取 64 位标记，通过 CRC 后，按完整 ID 精确查目录。未知 ID、低对比、CRC 错、缺数据或旧控制代次均不更新同步区域。
6. 图像、28 关节、底盘、日志时间和游标在同一个 canvas 回调内完成绘制。原生 video 仅作传输诊断，在同步模式中隐藏，不能先行展示未配对画面。

浏览器独立测试 oracle 不导入客户端的标记解析实现，而是原子读取最终 canvas 像素与已呈现快照，重新计算完整 ID 和 CRC。截图和录屏用于复查；这证明浏览器合成画布的同帧对应，不宣称测到了物理显示器扫描时间。

## 有界与故障行为

- 源端最多保留 512 份待验证状态、16 份目录状态；ID 耗尽会失败，不回绕复用。
- 主线程两侧缓存各最多 90 项，延迟队列最多 90 项；淘汰和清理时关闭 VideoFrame。
- 解码 pending 最多 90 项；丢失参考帧或解码失败后等待新 IDR。没有 latest-state fallback。
- 暂停/seek/step/stop 等控制以已接受的 request_id 建屏障，返回 HTTP 成功不等于已经显示。
- 同一连接固定会话；重连提升本地连接代次，旧异步结果不能重新呈现。
- 图像或数据迟到时保留整个已呈现配对；健康与等待提示仍可更新。
- 实验控制邮箱使用可精确传入 JavaScript 的持久化整数序列，拒绝耗尽；发送异常会使独立源探针报告失败。

## 已取得的证据

`outputs/p0/catalog-sync-no-viewport-v2/` 三个真实 Chrome 场景全部通过：正常播放、元数据额外延迟 700ms、视频额外延迟 700ms。源端 631/631 raw ID+CRC 校验通过；每个场景均有独立最终画布采样，未检出错配。

| 初始稳定呈现窗口 | 浏览器呈现 fps | 共同延迟中位数 | P95 | 最大值 |
|---|---:|---:|---:|---:|
| 正常，35 次呈现 | 18.63 | 96ms | 159ms | 171ms |
| 数据延迟 700ms，35 次呈现 | 18.93 | 797ms | 843ms | 849ms |
| 视频延迟 700ms，35 次呈现 | 19.68 | 798ms | 816ms | 846ms |

上述是短窗口测量，不是长时间承诺。含控制屏障等待的全段呈现率更低，JSON 中另行保留。共同延迟用同机源端 `captured_wall_s` 到浏览器实际 canvas 绘制时刻计算；不是远程时钟同步测量。

性能优化仅关闭同步模式中多余的默认 viewport，并保证独立相机产品与它不同。相关[官方性能说明](https://docs.isaacsim.omniverse.nvidia.com/6.2.0/reference_material/sim_performance_optimization_handbook.html)和实际产品路径都已记录。原 framebuffer RTSP 模式保持 viewport 开启。

## 验收边界

最终复测 `outputs/p0/catalog-sync-final/` 的三组用例全部通过，源端 1994/1994 原始标记验证通过。浏览器累计 1495 次配对呈现，688 次独立画布采样，0 次标记错配；同步模式两轮断开/重连均检查了冻结画布、DELETE、PC 关闭与网关会话释放。

其中 60 秒连续播放窗口新增 1177 次呈现，**19.61fps**，独立采样 561 次。正常场景包含重连的共同延迟中位数 **94.7ms**、P95 **147.6ms**、最大 **907.2ms**；两个额外延迟场景的中位数约 798ms、最大分别 880ms 和 850ms。完整统计见 [结构化证据](p0-whep-sync-evidence.json)。

三组 WebM 录屏已保存，分别带 SHA256。额外提取基线录屏 5 秒、40 秒两帧，独立像素解码为 112、780，与人工读取的 canvas 文本 ID 一致。此项是录屏抽查，不能称为全录屏逐帧 OCR 验证。自动浏览器测试的每次实际呈现仍执行客户端图像 ID+CRC 选择，独立 oracle 则按采样检查。

CPU 套件 86 项与浏览器能力/独立 CRC oracle 4 项通过；独立审查的两项 P2 已修复并复核。录屏工具初始化失败的旧运行 `catalog-sync-acceptance` 已保存为失败，不计入以上通过结果。

本轮支持范围是已验证的系统 Chrome 152、本机 WHEP、WebCodecs H.264 与临时 headless profile。正式前端需要能力检测。后续运动故障测试已补齐消息丢弃/乱序/重复、实际媒体中断、网关/worker 崩溃与浏览器刷新，见 [故障报告](p0-faults.md)。IP/RTP 丢包压力与 30 分钟稳定性仍未完成。

当前沿用原计划的初始性能目标 ≥15fps、共同延迟 <2s。用户已确认沿用该门槛。图像完整 ID+CRC 是当前可行候选；若未来 SDK 提供可信编码输出 ID，可替换传输身份机制，但必须复做像素与快照的独立验证。
